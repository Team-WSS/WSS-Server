# 컬렉션 정책

이 문서는 컬렉션 기능에서 지켜야 하는 도메인 규칙과 각 기능의 처리 흐름, 그리고 신규 테이블과 제약조건을 정리한다.
현재 적용 범위는 컬렉션 생성·수정·삭제(#560), 목록·상세 조회 및 접근 정책(#561), 좋아요(#562)다.

## 1. 컬렉션

- 컬렉션은 사용자가 작품을 주제별로 묶은 단위이며 소유자는 컬렉션을 만든 사용자 한 명이다.
- 사용자별 컬렉션 생성 개수는 제한하지 않는다.
- 한 사용자가 동일한 이름의 컬렉션을 여러 개 만들 수 있다. 따라서 이름은 컬렉션 식별자가 될 수 없다.
- 컬렉션 이름은 필수이며 공백을 포함해 20자 이하이다.
- 컬렉션 설명은 선택이며 60자 이하이다.
- 컬렉션은 기본적으로 공개 상태로 생성한다.
- 컬렉션에는 최소 1개, 최대 100개의 작품을 포함할 수 있다.
- 같은 작품을 한 컬렉션에 중복으로 포함할 수 없다.
- 대표 작품은 클라이언트가 지정하며 반드시 해당 컬렉션에 포함된 작품이어야 한다.

도메인 클래스 이름은 `Collection`을 사용한다. `java.util.Collection`과 단순 이름이 겹치지만 컬렉션을 가리키는
도메인 용어를 우선하며, 이 패키지의 코드는 `java.util.Collection`을 사용하지 않고 항상 `List`/`Set` 등 구체 타입을 쓴다.

## 2. 이름과 설명 처리

- 이름은 `null`, 빈 문자열, 공백만 있는 문자열을 모두 거부한다.
- 이름의 앞뒤 공백은 제거하지 않는다. 이름 길이 기준이 "공백을 포함해 20자 이하"이므로 공백도 글자 수에 센다.
- 설명은 `null`, 빈 문자열, 공백만 있는 문자열을 모두 `null`로 정규화해 저장한다.
  조회 응답이 "설명 없음"을 한 가지 값으로만 표현하도록 하기 위함이다.
- 수정 요청에서 설명을 `null`이나 빈 문자열로 보내면 설명 삭제로 해석한다.

## 3. 공개 여부

- 생성 요청에서 공개 여부를 생략하면 서버가 공개(`true`)로 생성한다.
- 수정 요청에서는 공개 여부를 필수로 받는다. 생략을 공개로 해석하면 비공개 컬렉션을 수정할 때 필드를 빠뜨리는
  것만으로 컬렉션이 조용히 공개로 바뀌기 때문이다.

컬렉션은 항상 공개이거나 비공개이며 "값이 없는" 상태가 없다. 반면 요청 DTO는 값이 생략됐는지를 알아야 한다.
그래서 요청 DTO와 엔티티가 서로 다른 타입을 쓴다.

| 위치 | 타입 | 이유 |
|---|---|---|
| `CollectionCreateRequest.isPublic` | `Boolean` | 생략(`null`)과 명시적인 `false`를 구분해야 기본값 공개를 적용할 수 있다 |
| `CollectionUpdateRequest.isPublic` | `@NotNull Boolean` | 생략을 조용히 `false`로 처리하지 않고 검증 오류로 돌려보낸다 |
| `Collection.isPublic` | `boolean` | 비어 있을 수 없는 값이므로 원시 타입으로 불변식을 타입에 담는다 |

생성 팩터리만 입력 경계에서 `Boolean`을 받고, 기본값 적용은 엔티티 생성자가 책임진다.
생성자가 `null`을 `DEFAULT_IS_PUBLIC`(`true`)로 정규화한 뒤 원시 타입 필드에 저장하므로,
어떤 경로로 컬렉션을 만들어도 공개 여부는 항상 결정된 값으로 저장된다. 명시적인 `false`는 그대로 `false`다.
수정은 이미 `@NotNull`로 검증된 값만 받으므로 `boolean`을 그대로 받는다.
엔티티가 원시 타입이므로 접근자 이름은 `getIsPublic()`이 아니라 `isPublic()`이다.

기본값은 DB `DEFAULT`로 선언하지 않는다. `is_public`은 `NOT NULL`이고 애플리케이션이 항상 값을 채워 넣으므로
DB 기본값은 실제로 쓰이지 않으면서 "기본 공개"라는 정책을 애플리케이션과 DB 두 곳에 중복으로 두게 된다.
정책이 바뀌면 코드와 DDL을 함께 고쳐야 하고, DB 종속적인 `columnDefinition` 문자열이 엔티티에 남는다.

## 4. 컬렉션 생성

`POST /collections`를 사용하며 로그인한 사용자만 요청할 수 있다.

1. 작품 수가 1개 이상 100개 이하인지 확인한다.
2. 같은 작품이 중복으로 포함되지 않았는지 확인한다.
3. 대표 작품이 포함 작품 중 하나인지 확인한다.
4. 요청한 작품이 모두 존재하는지 한 번의 조회로 확인한다.
5. 컬렉션과 컬렉션 작품을 저장한다.

- 성공하면 `201 Created`와 생성된 `collectionId`를 반환한다.
  같은 사용자가 같은 이름의 컬렉션을 여러 개 만들 수 있어 클라이언트가 이름으로 방금 만든 컬렉션을 찾을 수 없으므로,
  생성 직후 상세 조회와 공유를 위해 식별자를 반환한다.
- 요청한 작품은 요청 배열 순서대로 저장한다. 같은 요청으로 추가된 작품끼리도 식별자 순서가 결정적으로 정해진다.

## 5. 컬렉션 수정

`PUT /collections/{collectionId}`를 사용하며 소유자만 요청할 수 있다. 성공하면 `204 No Content`를 반환한다.

1. 컬렉션이 존재하는지 확인한다.
2. 요청한 사용자가 소유자인지 확인한다.
3. 작품 수, 중복 작품, 대표 작품 포함 여부를 확인한다.
4. 요청한 작품이 모두 존재하는지 한 번의 조회로 확인한다.
5. 이름, 설명, 공개 여부, 대표 작품을 갱신하고 포함 작품을 delta로 갱신한다.

### 5.1 포함 작품은 delta로만 갱신한다

수정 요청은 전체 교체 의미로 받지만 내부적으로는 전체 삭제 후 재삽입을 하지 않는다.

- 제거된 작품만 삭제한다.
- 새로 추가된 작품만 저장한다.
- 계속 포함되는 작품의 `collection_novel` 행은 손대지 않는다.

이유는 두 가지다.

1. `collection_novel.created_date`는 "작품이 컬렉션에 추가된 시점"을 뜻하며 #561의 최근 추가 작품 미리보기와
   추가 시점 기준 정렬의 기준값이다. 전체 삭제 후 재삽입하면 컬렉션을 수정할 때마다 모든 작품의 추가 시점이
   수정 시각으로 리셋되어 정렬 기준이 무의미해지고, 과거 값을 복구할 수 없다.
2. 같은 트랜잭션에서 같은 `(collection_id, novel_id)`를 삭제하고 다시 저장하면 유니크 제약 위반이 발생한다.
   Hibernate는 저장을 삭제보다 먼저 반영하기 때문이다. delta 갱신은 애초에 재삽입을 하지 않아 이 문제가 없다.

컬렉션 자체의 `modified_date`는 수정 시각으로 갱신되므로 언제 수정했는지는 그대로 남는다.
`collection.created_date`는 바뀌지 않으므로 #561의 "최초 생성 시점 기준" 컬렉션 정렬도 영향을 받지 않는다.

### 5.2 수정 시각은 명시적으로 갱신한다

검증을 통과한 수정은 이름·설명·공개 여부·대표 작품이 이전과 같더라도 항상 `collection.modified_date`를 갱신한다.

포함 작품만 바뀌면 `collection` 행 자체는 변경되지 않아 자동 갱신되는 `modified_date`가 그대로 남는다.
따라서 도메인이 수정 끝에 명시적으로 수정 시각을 표시한다.
서재 평가에서 자식만 바뀐 경우 `UserNovel.touch()`를 호출하는 기존 방식과 같다.

정책 위반으로 실패한 수정은 아무것도 바꾸지 않으므로 수정 시각도 갱신하지 않는다.

### 5.3 동시 수정은 컬렉션 단위로 직렬화한다

수정과 삭제는 대상 컬렉션 행에 쓰기 잠금을 걸고 시작한다.
잠금이 없으면 같은 컬렉션에 대한 동시 수정 요청이 각자 읽은 포함 작품을 기준으로 delta를 계산해
서로의 변경을 덮어쓸 수 있다.

- 잠그는 대상은 `collection` 루트 행 하나뿐이다.
- 포함 작품까지 조인해 잠그지 않는다. 여러 컬렉션이 공유하는 `novel` 행을 잠그게 되어
  서로 무관한 컬렉션 수정끼리 대기하기 때문이다.
- 조회 전용 경로는 잠금 조회를 사용하지 않는다. 목록·상세 조회(8·9절)는 잠금 없는 조회를 쓴다.

- 포함 작품이 모두 제거되는 수정은 허용하지 않는다. 빈 컬렉션이 필요하면 컬렉션 자체를 삭제한다.
- 수정으로 대표 작품이 제거되는 경우 클라이언트가 변경된 대표 작품을 함께 전달해야 한다.

## 6. 컬렉션 삭제

`DELETE /collections/{collectionId}`를 사용하며 소유자만 요청할 수 있다. 성공하면 `204 No Content`를 반환한다.

- 컬렉션 작품은 컬렉션과 같은 애그리거트이므로 `cascade`와 `orphanRemoval`로 함께 삭제된다.
- 컬렉션 좋아요는 별도 애그리거트이므로 컬렉션 엔티티에 매핑하지 않는다. 따라서 `cascade`로 따라 지워지지 않고
  `CollectionManagementApplication.delete`가 컬렉션보다 **먼저** 좋아요를 지운다(16.5절).
  피드 삭제가 댓글·좋아요를 Application에서 순서대로 지우는 기존 방식과 같다.
- 삭제는 hard delete이며 soft delete를 사용하지 않는다.
- 삭제도 수정과 같은 잠금 조회로 대상 컬렉션을 가져온다.

### 6.1 회원 탈퇴 시 컬렉션 정리

탈퇴한 사용자의 컬렉션은 삭제하지 않고 보존한다. 피드·댓글 작성자 익명화와 같은 방식으로
소유자만 알 수 없는 사용자(`user_id = -1`)로 넘긴다. 컬렉션은 다른 사용자가 이미 보고 있을 수 있는
공개 콘텐츠이므로, 작성자가 탈퇴했다는 이유만으로 내용까지 사라지지 않게 한다.

- 컬렉션은 소유자가 반드시 있어야 하므로(`collection.user_id`가 NOT NULL) 사용자를 지우기 전에 소유자를 옮긴다.
- 알 수 없는 사용자 `-1`이 존재한다는 전제는 기존 피드·댓글 익명화와 같다. 새로 만들지 않는다.
- `collection.user_id`의 외래 키(`fk_collection_user`)에는 `ON DELETE CASCADE`를 걸지 않는다.
  정리 책임은 DB가 아니라 애플리케이션에 둔다. 탈퇴 흐름에서 어떤 데이터가 어떻게 처리되는지
  코드에서 드러나야 하고, 기존 탈퇴 정리(리프레시 토큰 삭제, 피드·댓글 작성자 익명화)도 같은 방식이기 때문이다.
- `AccountApplication`의 탈퇴 정리에서 피드·댓글 작성자 익명화와 나란히, 사용자 삭제 전에 소유자를 넘긴다.
- 소유자 이관은 QueryDSL `update`로 `collection.user_id`만 한 번에 갱신한다.
  컬렉션을 엔티티로 불러올 이유가 없고 자식 행(`collection_novel`)은 손대지 않으므로,
  삭제와 달리 벌크 갱신으로 인해 놓치는 cascade 동작이 없다.
- `collection_novel`은 컬렉션을 그대로 따라가므로 별도 정리가 필요 없다.
- 탈퇴한 사용자가 **남긴** 좋아요는 지우지 않는다(16.6절). 컬렉션 자체가 보존되므로 컬렉션에 **달린**
  좋아요도 탈퇴와 함께 정리할 필요가 없다.

컬렉션 삭제 API(6절)의 hard delete는 그대로 유지한다. 소유자가 직접 지운 컬렉션과
소유자가 탈퇴해 주인이 없어진 컬렉션은 다른 상황이다.

## 7. 소유자 권한

- 컬렉션 수정과 삭제는 소유자만 할 수 있다.
- 소유자가 아니면 `403 Forbidden`을 반환한다.
- 소유권 검증은 Controller가 아니라 컬렉션 엔티티(`Collection.validateOwner`)에서 수행한다.
  HTTP 진입점이 달라져도 같은 정책을 적용한다.

## 8. 컬렉션 목록 조회

`GET /users/{userId}/collections`를 사용하며 로그인한 사용자만 요청할 수 있다. 성공하면 `200 OK`를 반환한다.

1. 페이지 크기가 1 이상 100 이하인지 확인한다.
2. 컬렉션 주인이 존재하는지 확인한다.
3. 조회자와 컬렉션 주인이 차단 관계인지 확인한다.
4. 본인 조회면 비공개 컬렉션까지, 아니면 공개 컬렉션만 읽는다.
5. 커서 다음 컬렉션을 요청 크기보다 하나 더 읽어 다음 페이지 존재 여부를 판단한다.
6. 이번 페이지 컬렉션의 최근 추가 작품 미리보기를 한 번의 조회로 채운다.

- 목록은 컬렉션의 최초 생성 시점(`collection.created_date`) 내림차순으로 정렬한다. 수정 시점이 아니다.
  컬렉션을 수정할 때마다 목록 순서가 바뀌면 사용자가 만든 순서를 기준으로 한 탐색이 흔들리기 때문이다.
- 응답에는 조회 가능한 전체 컬렉션 개수를 함께 준다. 페이지 크기와 무관한 값이므로 마이페이지가
  `size=3`으로 호출해도 "컬렉션 N개"를 그대로 표시할 수 있다.
- 마이페이지 미리보기 전용 API를 따로 두지 않는다. 같은 목록 API를 `size=3`으로 호출한다.
- 컬렉션 카드에는 대표 작품(`representativeNovel`)과 최근 추가 작품(`recentNovels`), 포함 작품 수를 함께 준다.
- 대표 작품과 최근 추가 작품은 서로 독립적인 값이다. 대표 작품은 카드 표지로 쓰는 작품 하나이고,
  최근 추가 작품은 최근에 추가된 작품부터 최대 5개다. 대표 작품을 최근 추가 작품에서 걸러 내지 않으므로
  대표 작품이 최근에 추가된 작품이면 두 곳에 같은 작품이 함께 나간다. 이는 정상 응답이며 서버가 중복을 제거하지 않는다.
  화면이 대표 작품을 미리보기 줄에서 뺄지는 클라이언트가 정한다.
- `novelCount`는 최근 추가 작품의 개수가 아니라 컬렉션에 포함된 전체 작품 수다.

### 8.1 커서는 생성 시점과 식별자를 함께 담는다

무한 스크롤을 고려해 offset이 아니라 커서 기반 페이지네이션을 사용한다.

- 커서는 마지막으로 읽은 컬렉션의 `created_date`와 `collection_id`를 함께 담는다.
  같은 시각에 만들어진 컬렉션이 있어도 식별자가 순서를 결정적으로 정하므로 중복과 누락이 생기지 않는다.
- 식별자만 넘기고 서버가 그 컬렉션의 생성 시각을 다시 조회하지 않는다.
  커서로 쓰던 컬렉션이 삭제되면 기준 시각을 잃어 페이지네이션이 깨지기 때문이다.
- 커서는 Base64로 인코딩해 불투명한 문자열로 준다. 클라이언트는 해석하지 않고 다음 요청에 그대로 돌려준다.
- 서버가 발급하지 않은 커서는 조회 조건으로 쓰지 않고 `COLLECTION-007`로 거부한다.
- 다음 페이지가 없으면 커서를 내려보내지 않는다. `hasNext`와 커서 유무를 항상 일치시킨다.
- 인덱스 `idx_collection_user_created (user_id, created_date, collection_id)`가 이 정렬과 커서 조건을 받는다.

## 9. 컬렉션 상세 조회

`GET /collections/{collectionId}`를 사용한다. 인증은 선택이며 성공하면 `200 OK`를 반환한다.

1. 컬렉션이 존재하는지 확인하고 공개 여부와 소유자를 읽는다.
2. 로그인 조회자와 소유자가 차단 관계인지 확인한다.
3. 비공개 컬렉션이면 소유자인지 확인한다.
4. 포함 작품을 요청한 추가 시점 정렬 기준으로 읽는다.

- 포함 작품은 식별자만 주지 않고 목록 카드와 같은 작품 요약(9.1절)을 함께 준다.
  클라이언트가 작품 수만큼 상세를 다시 조회하지 않게 하기 위함이다.
- 포함 작품은 컬렉션에 추가된 시점(`collection_novel.created_date`) 기준으로 최신순·오래된순을 지원한다.
  기존 `SortCriteria`(`RECENT`/`OLD`)를 그대로 쓰고, 생략하면 최신순이다.
- 같은 요청으로 여러 작품을 동시에 추가하면 추가 시점이 같을 수 있으므로 `collection_novel_id`를
  보조 정렬 기준으로 함께 사용해 순서를 결정적으로 만든다.
- 상세는 소유자 정보를 함께 준다. 공유 링크로 들어온 조회자에게 누가 만든 컬렉션인지
  보여 줘야 하고, 조회자가 소유자인지(`isMyCollection`) 판단하는 데도 필요하다.
- 소유자 정보는 평면 필드로 흩뿌리지 않고 `owner` 객체(`userId`, `nickname`, `avatarImage`)로 묶는다.
  컬렉션 자체의 값과 소유자의 값이 같은 깊이에 섞이면 어느 값이 무엇에 속하는지 응답만 보고 알 수 없다.
- `owner.avatarImage`는 항상 값이 있다. 아바타는 모든 사용자가 반드시 가지므로(`user.avatar_profile_id`가
  `NOT NULL`) 조회 쿼리도 아바타를 inner join으로 읽는다. outer join으로 읽으면 아바타가 없는 사용자를 정상으로
  취급해 응답이 조용히 비고, 클라이언트가 있을 수 없는 상태를 처리해야 한다.
- 상세에는 페이지네이션을 두지 않는다. 컬렉션의 포함 작품은 최대 100개로 제한돼 있다(1절).

### 9.1 목록과 상세는 하나의 작품 요약 구조를 공유한다

목록의 대표 작품과 최근 추가 작품, 상세의 포함 작품은 모두 같은 작품 요약을 내보낸다.
응답 DTO도 `CollectionNovelSummaryGetResponse` 하나를 공유한다.

| 필드 | 설명 |
|---|---|
| `novelId` | 작품 ID |
| `title` | 작품 제목 |
| `novelImage` | 작품 표지 이미지 URL |
| `author` | 작가 |

- 같은 작품을 가리키는 값이 화면마다 다른 모양으로 나가면 클라이언트가 작품 카드를 그리는 코드를 위치마다
  따로 두게 된다. 컬렉션 화면에서 작품을 보여 주는 방식은 하나이므로 응답 구조도 하나로 둔다.
- 완결 여부(`isCompleted`), 평점(`novelRating`), 평점 수(`novelRatingCount`)는 내보내지 않는다.
  컬렉션 화면이 쓰지 않는 값이며, 이 값을 위해 상세 조회가 작품 통계(`novel_statistics`)를 조인해야 했다.
  필요해지면 작품 상세 API에서 읽는다.
- 따라서 상세의 포함 작품 조회는 작품 통계를 조인하지 않고 작품 테이블만 읽는다.

### 9.2 인증은 선택이지만 토큰을 보냈다면 유효해야 한다

공유 링크로 들어온 비로그인 사용자가 공개 컬렉션을 볼 수 있어야 하므로 상세 조회만 인증을 선택으로 둔다.

- `SecurityConfig`에서 `GET /collections/{collectionId}`만 인증 없이 열고, 메서드를 함께 지정한다.
  경로만 열면 같은 경로의 수정·삭제까지 필터 단계에서 열려 인증 실패가 401이 아닌 403으로 바뀐다.
- `Authorization` 헤더가 없으면 비로그인 조회로 처리한다.
- 헤더를 보냈다면 토큰은 유효해야 한다. 만료·위조·타입 오류는 그대로 401이다.
  이는 기존 `JwtAuthenticationFilter`의 동작이며 이 API를 위해 바꾸지 않는다.
- 컬렉션 목록은 인증을 선택으로 두지 않는다. 본인 목록에만 비공개 컬렉션이 포함되므로
  조회자가 누구인지 모르면 공개 범위를 정할 수 없다.

## 10. 조회 공개 범위와 차단

| 조회자 | 목록 | 상세 |
|---|---|---|
| 본인 | 공개·비공개 모두 | 공개·비공개 모두 |
| 다른 로그인 사용자 | 공개만 | 공개만 |
| 비로그인 | 조회 불가(401) | 공개만 |
| 차단 관계인 로그인 사용자 | 조회 불가(403) | 조회 불가(403) |

- 차단은 어느 방향이든 적용한다. 조회자가 소유자를 차단했든 소유자가 조회자를 차단했든 결과는 같다.
- 차단 검증은 공개 여부 검증보다 먼저 한다. 차단 관계라면 공개 컬렉션이어도 볼 수 없다.
- 목록은 차단 관계인 사용자의 컬렉션을 걸러 내는 대신 목록 자체를 거부한다.
  한 사용자의 컬렉션만 모아 보여 주는 목록이라 빈 목록과 접근 거부가 사실상 같기 때문이다.
- 비로그인 조회에는 차단 관계가 없다(`BLOCK_POLICY.md` 1절).
- 비공개 컬렉션에 대한 접근 거부는 `404`가 아니라 `403`이다. 숨김 피드 접근을 `403`으로 돌려주는
  기존 방식과 같게 두고, 조회 API마다 존재 여부 노출 정책이 갈리지 않게 한다.

## 11. 오류 처리

작품 수, 중복 작품, 대표 작품 정책 위반은 모두 컬렉션 도메인 예외로 처리한다.
따라서 이 세 가지는 요청 DTO의 Bean Validation으로 검증하지 않는다. DTO는 `null` 여부와 문자열 길이만 검증한다.

| 코드 | 상황 | 상태 |
|---|---|---|
| `COLLECTION-001` | 해당 ID를 가진 컬렉션이 없음 | 404 |
| `COLLECTION-002` | 작품 수가 1개 미만이거나 100개 초과 | 400 |
| `COLLECTION-003` | 같은 작품을 중복으로 포함 | 400 |
| `COLLECTION-004` | 대표 작품이 포함 작품이 아님 | 400 |
| `COLLECTION-005` | 소유자가 아닌 사용자의 수정·삭제 요청 | 403 |
| `COLLECTION-006` | 소유자가 아닌 사용자의 비공개 컬렉션 접근 요청(상세 조회, 좋아요 등록·취소) | 403 |
| `COLLECTION-007` | 서버가 발급하지 않았거나 형식이 어긋난 목록 커서 | 400 |
| `COLLECTION-008` | 목록 페이지 크기가 1 미만이거나 100 초과 | 400 |
| `BLOCK-007` | 조회자와 컬렉션 소유자가 차단 관계 | 403 |
| `NOVEL-001` | 요청한 작품이 존재하지 않음 | 404 |

요청한 작품의 존재 검증은 컬렉션 전용 오류를 새로 만들지 않고 기존 작품 도메인 오류를 재사용한다.

좋아요 기능은 오류 코드를 새로 만들지 않는다. 좋아요를 누를 수 있는 컬렉션인지는 상세 조회와 같은 판정이므로
같은 코드를 쓰고, 중복 등록과 이미 취소된 좋아요는 오류가 아니라 성공이다(16.2절).
좋아요한 컬렉션 목록의 커서와 페이지 크기도 사용자별 컬렉션 목록과 같은 코드를 쓴다. 두 목록의 커서는 서로
가리키는 대상이 다르지만(16.4절), 클라이언트 입장에서는 "이 API가 발급하지 않은 커서"라는 같은 오류다.

## 12. 구현 구조

저장소 공통 규칙(`CLAUDE.md`)을 컬렉션 기능에도 그대로 적용한다.

### 12.1 쿼리는 QueryDSL로 직접 작성한다

- 커스텀 쿼리를 `@Query` 어노테이션으로 표현하지 않는다.
- `CollectionCustomRepository` 인터페이스에 쿼리를 선언하고 `CollectionCustomRepositoryImpl`에서
  `JPAQueryFactory`와 생성된 Q 타입으로 구현한다.
- `CollectionRepository`는 `JpaRepository`와 `CollectionCustomRepository`를 함께 상속한다.
- 쓰기 잠금은 어노테이션이 아니라 QueryDSL의 `setLockMode(LockModeType.PESSIMISTIC_WRITE)`로 지정한다.
- 포함 작품을 함께 읽는 조회는 `fetchJoin()`으로 한 번에 가져와 작품 수만큼 추가 조회가 생기지 않게 한다.
  fetch join은 컬렉션 하나를 작품 수만큼의 행으로 돌려주므로 중복을 제거한 뒤 사용한다.

예외는 좋아요 등록의 upsert 하나다. JPQL에도 QueryDSL JPA에도 `INSERT`가 없고,
`ON DUPLICATE KEY UPDATE`는 MySQL 문법이므로 JPA로는 표현할 수 없다(16.2절).

- 이 문장은 `@Query(nativeQuery = true)`가 아니라 `JdbcTemplate`으로 실행한다. 커스텀 리포지토리 구현이
  쿼리를 소유한다는 구조는 그대로 두고, 인터페이스 선언에 SQL 문자열이 딸려 오지 않게 한다.
- SQL의 테이블명·컬럼명·제약조건은 14.3절의 정의와 정확히 같아야 한다. 매핑을 거치지 않으므로 이름이
  어긋나도 애플리케이션이 뜰 때는 드러나지 않는다. 조립된 문장을 단위 테스트로 고정한다(15절).
- `INSERT IGNORE`는 쓰지 않는다. 유니크 위반뿐 아니라 외래 키 위반까지 경고로 낮춰 삼키므로,
  사라진 컬렉션에 대한 좋아요가 조용히 성공으로 끝난다(16.7절).

### 12.2 조회 전용 쿼리는 엔티티가 아니라 projection으로 읽는다

목록·상세 조회는 엔티티를 다루는 `CollectionCustomRepository`와 분리해
`CollectionQueryRepository` 인터페이스와 `CollectionQueryRepositoryImpl`에 둔다.
`CollectionRepository`가 상속하는 Spring Data 조각이 아니라 독립 `@Repository` 빈이며,
피드·댓글의 `XxxQueryRepository` 구조와 같다.

- 조회 결과는 엔티티가 아니라 `Projections.constructor`로 projection 레코드에 매핑한다.
- 화면 하나를 그리는 데 쓰는 쿼리 수는 목록 3개(페이지·전체 개수·미리보기),
  상세 2개(컬렉션·포함 작품)에 로그인 조회의 좋아요 여부 1개를 더한 값으로 고정한다.
  좋아요한 컬렉션 목록도 사용자별 컬렉션 목록과 같은 3개다.
  컬렉션 수나 작품 수, 좋아요 수에 비례해 쿼리가 늘지 않는다.
- 카드의 대표 작품은 목록 쿼리에서 함께 조인하고, 포함 작품 수와 좋아요 수는 같은 쿼리의 서브 쿼리로 센다.
- 컬렉션별 최근 추가 작품 최대 5개는 JPQL에 윈도 함수가 없으므로,
  같은 컬렉션에서 자기보다 나중에 추가된 작품 수가 5개 미만인 행만 고르는 조건으로 한 번에 읽는다.
  컬렉션마다 미리보기를 따로 조회하지 않고, 컬렉션당 최대 5행만 돌려받는다.
- 목록의 대표 작품·최근 추가 작품과 상세의 포함 작품은 같은 작품 요약(9.1절)을 내보내므로 모두 작품 테이블만
  읽는다. 상세 작품 조회는 작품 통계(`novel_statistics`)를 조인하지 않는다.
- 조인 종류는 값의 필수 여부에 맞춘다. 소유자와 소유자의 아바타는 반드시 있으므로 inner join으로 읽고,
  대표 작품은 작품이 지워진 컬렉션에서도 조회가 실패하지 않도록 outer join으로 읽는다.
  없을 수 없는 값을 outer join으로 읽으면 없는 상태를 정상으로 취급해 응답이 조용히 비게 된다.

### 12.3 API 문서는 실제 응답을 문서화하고 구조는 필드 서술로 드러낸다

Swagger UI가 읽는 OpenAPI 명세는 손으로 쓰지 않고 REST Docs 문서 테스트(`*DocsTest`)가 실제로 주고받은
요청·응답에서 생성한다. 따라서 문서에 적힌 구조는 항상 실제 JSON 계약과 같다.

- 응답 예시는 실제 응답 DTO로 만든다. 예시는 계약을 이해하는 데 필요한 경계까지 담는다.
  목록 성공 예시의 `recentNovels`는 최대치인 5개로 만들고 대표 작품을 그 안에 함께 넣는다.
  두 개짜리 예시로는 최대 개수도, 대표 작품이 중복될 수 있다는 사실도 예시에서 읽히지 않는다.
- 생성기(`restdocs-api-spec`)는 요청·응답 루트에만 스키마 이름을 붙이고 중첩 객체는 인라인으로 펼친다.
  따라서 `owner`나 공통 작품 요약에 독립 스키마 이름을 줄 수 없다. 실제 계약에 없는 이름을 문서에만 만들어
  붙이지 않고, 각 겹이 무엇이고 어디에 쓰이는지는 필드 서술과 엔드포인트 서술이 담는다.
- 목록 응답은 페이지 정보·컬렉션 카드·작품 요약 세 겹이므로 필드 서술에 어느 겹의 값인지 표시하고,
  상세와 공유하는 작품 요약에는 같은 구조라는 사실을 함께 적는다.
- 서로 오해하기 쉬운 값은 서술에서 명시적으로 구분한다.
  `collectionsCount`는 이번 페이지 개수가 아니고, `novelCount`는 `recentNovels`의 개수가 아니다.

### 12.4 유스케이스 트랜잭션 경계는 Application이 소유하고 Service는 메서드 단위 속성을 명시한다

- 컬렉션 생성·수정·삭제 유스케이스 전체의 트랜잭션은 `CollectionManagementApplication`이 연다.
- 회원 탈퇴 유스케이스 전체의 트랜잭션은 `AccountApplication`이 연다.
- `CollectionService`의 Repository 접근 public 메서드는 각자 필요한 트랜잭션 속성을 명시한다.
  Service를 어디서 호출하든 그 메서드에 필요한 트랜잭션 속성이 코드에 드러나야 하기 때문이다.

| 메서드 | 속성 | 이유 |
|---|---|---|
| `create` | `@Transactional` | 저장 후 즉시 반영하는 데이터 변경 |
| `flushChanges` | `@Transactional` | 변경 감지 결과를 즉시 반영 |
| `delete` | `@Transactional` | 데이터 변경 |
| `updateOwnerToUnknown` | `@Transactional` | 탈퇴 시 소유자 벌크 갱신 |
| `getOwnedCollectionOrException` | `@Transactional` | 조회만 하지만 비관적 쓰기 잠금이 필요해 읽기 전용으로 둘 수 없다 |
| `getCollectionOrException` | `@Transactional(readOnly = true)` | 잠금 없는 단순 조회 |
| `getCollectionAccessOrException` | `@Transactional(readOnly = true)` | 공개 여부와 소유자만 필요한 경로의 조회 |

- 컬렉션 목록·상세 조회 유스케이스 전체의 트랜잭션은 `CollectionFindApplication`이 읽기 전용으로 연다.
- `CollectionQueryService`는 조회 전용 Repository 접근을 캡슐화하며 모든 메서드가
  `@Transactional(readOnly = true)`다.
- 좋아요 취소 유스케이스 전체의 트랜잭션은 `CollectionLikeApplication`이,
  좋아요한 컬렉션 목록 조회는 `CollectionLikeFindApplication`이 읽기 전용으로 연다.
- 좋아요 등록만은 유스케이스 트랜잭션을 열지 않는다(12.5절).
- `CollectionLikeService`는 좋아요 영속화를, `CollectionLikeQueryService`는 좋아요 목록 조회를
  캡슐화하며 모든 메서드가 필요한 트랜잭션 속성을 애너테이션으로 명시한다.
  트랜잭션 경계를 코드로 다루는 `TransactionTemplate`이나 주입된 `PlatformTransactionManager`는 두지 않는다.
- Service는 다른 Service를 호출하지 않는다. 여러 Service를 조합하는 것은 Application의 책임이며,
  Service끼리 부르면 유스케이스 트랜잭션 경계가 어디인지 코드에서 읽히지 않는다.

- 전파 속성은 모두 기본값(`REQUIRED`)이다.
  Application이 이미 트랜잭션을 열었으면 새로 열지 않고 참여하므로,
  유스케이스 전체가 하나의 트랜잭션으로 묶인다는 사실은 그대로다.
- 따라서 쓰기 잠금, 지연 로딩, `flush`, 연쇄 삭제는 여전히 Application이 연 하나의 트랜잭션 안에서 동작한다.
- 한 요청이 커넥션을 동시에 두 개 점유하는 구조는 두지 않는다. 바깥 트랜잭션이 커넥션을 쥔 채
  안쪽에서 `REQUIRES_NEW`로 또 하나를 요구하면, 커넥션 풀이 마르는 순간 두 요청이 서로의 커넥션을
  기다리며 풀리지 않는다. 새 트랜잭션이 필요하면 바깥 트랜잭션을 없애 순차적으로 실행한다.
- Service 단독 호출도 최소한 자기 메서드에 필요한 트랜잭션 안에서 동작한다.
  다만 여러 Service 호출을 하나의 원자적 단위로 묶는 책임은 여전히 Application에 있다.

### 12.5 좋아요 등록은 중복을 DB에 맡기고 유스케이스 트랜잭션을 열지 않는다

좋아요 등록의 어려움은 "이미 좋아요한 상태"를 어떻게 멱등하게 흡수하느냐였다. 애플리케이션에서 존재를
확인하고 저장하면 동시 요청이 둘 다 통과한 뒤 유니크 제약조건에서 갈리고, 그 위반을 **어느 트랜잭션에서
터뜨리고 어디서 받는지**를 계속 따져야 한다. 같은 트랜잭션에서 `flush`가 실패하면 JPA가 그 트랜잭션을
롤백 전용으로 표시하므로 예외를 잡아 정상 반환해도 커밋할 수 없고, 바깥 트랜잭션을 열어 둔 채 안쪽에서
`REQUIRES_NEW`로 저장하면 한 요청이 커넥션을 두 개 점유한다(12.4절).

그래서 중복 흡수를 애플리케이션이 아니라 **DB의 upsert 한 문장**에 맡긴다.

- 등록은 `INSERT ... ON DUPLICATE KEY UPDATE`(16.2절) 한 번이다. 중복이면 DB가 no-op으로 끝내므로
  유니크 제약조건 위반 자체가 발생하지 않는다. 잡을 예외가 없으니 판별을 트랜잭션 밖으로 뺄 이유도,
  트랜잭션 경계를 코드로 다룰 이유도 없다.
- 따라서 `CollectionLikeService.create`는 `@Transactional` 하나로 경계를 관리하고,
  `TransactionTemplate`도 주입된 `PlatformTransactionManager`도 두지 않는다.
- 사전 존재 확인(`exists`)도 하지 않는다. 동시 요청을 막지 못하면서 왕복만 늘리기 때문이다.
- 남는 실패는 등록하는 사이에 컬렉션이 삭제된 경우뿐이다. 이것은 서버 오류가 아니라 컬렉션을 찾을 수 없는
  요청이므로 `CollectionLikeService`가 `COLLECTION-001`로 바꿔 던진다. 예외를 던지므로 트랜잭션은
  롤백되고, 판별하지 못한 무결성 오류는 그대로 재전파한다(16.7절).
- 실패 판별은 등록하는 계층이 소유한다. 어떤 무결성 오류를 무엇으로 볼지는 영속화의 사정이므로,
  유스케이스는 등록을 호출할 뿐 `DataIntegrityViolationException`도 제약조건 판별기도 알지 않는다.
- `CollectionLikeApplication.create`는 그래도 유스케이스 트랜잭션을 열지 않는다. 접근 정책 검증(읽기)
  뒤에 등록 한 건으로 끝나 함께 원자적으로 되돌릴 후속 작업이 없고, 읽기와 쓰기가 순차적으로 각자의
  트랜잭션을 쓰면 어느 순간에도 커넥션이 하나이기 때문이다.
- 등록은 검증과 다른 트랜잭션이므로 Application이 그 뒤에 실패해도 좋아요는 남는다.
  좋아요 등록 뒤에 다른 데이터 변경을 덧붙이게 되면 이 경계를 다시 따져야 한다.
- 취소는 접근 검증과 삭제를 한 트랜잭션에 담아도 커넥션이 하나이므로 `delete`는 유스케이스 트랜잭션을
  그대로 소유한다.

### 12.6 트랜잭션 경계 사이에는 엔티티가 아니라 값을 넘긴다

좋아요 등록처럼 트랜잭션이 두 번 열리는 경로에서는, 앞 트랜잭션이 읽은 엔티티를 뒤 트랜잭션으로 넘기지 않는다.

- 넘기면 그 인스턴스를 관리하던 영속성 컨텍스트가 이미 닫힌 상태이므로 `collection.user` 같은 지연 로딩이
  깨지고, 뒤 트랜잭션이 다른 영속성 컨텍스트에 속한 엔티티를 참조하게 된다.
- 접근 정책 검증은 `CollectionAccess`(컬렉션 식별자·소유자·공개 여부)라는 값만 돌려받는다.
  비공개 판정도 이 값이 소유하므로 트랜잭션이 닫힌 뒤에 검증해도 된다.
- 등록에 넘기는 것도 식별자 두 개뿐이다. upsert는 영속성 컨텍스트를 거치지 않으므로 참조할 컬렉션
  엔티티를 읽을 필요조차 없다.

## 13. 데이터 무결성

- 같은 컬렉션에 같은 작품이 여러 번 저장되지 않아야 한다.
- 같은 사용자가 같은 컬렉션에 좋아요를 여러 번 저장하지 않아야 한다.
- `(collection_id, novel_id)`와 `(user_id, collection_id)` 유니크 제약조건을 애플리케이션 엔티티와
  실제 개발·운영 DB에 동일하게 적용한다.
- 컬렉션 작품 유니크 제약조건 이름은 `uk_collection_novel_collection_novel`을,
  컬렉션 좋아요 유니크 제약조건 이름은 `uk_collection_like_user_collection`을 사용한다.
- 컬렉션 좋아요가 컬렉션을 참조하는 외래 키 이름은 `fk_collection_like_collection`을 사용한다.
  실제 DB의 제약조건과 이 매핑이 같은 것을 가리킨다는 사실이 이름으로 드러나야 하기 때문이다(14.3절).
- 같은 컬렉션에 같은 작품을 추가하는 중복은 애플리케이션이 막는다. 생성과 수정은 저장 시점에 제약조건
  위반을 확인할 수 있도록 즉시 반영한 뒤, 해당 제약조건의 중복만 컬렉션 도메인 예외(`COLLECTION-003`)로
  변환한다. 지정한 제약조건 위반만 변환하고 그 외 데이터 무결성 오류는 숨기지 않는다.
  이는 동시에 같은 작품을 추가한 요청이 일반적인 DB 무결성 메시지로 노출되는 것을 막기 위한 방어다.
- 같은 사용자가 같은 컬렉션에 누르는 중복 좋아요는 애플리케이션이 아니라 DB가 흡수한다.
  upsert 한 문장이 정상 종료하므로 변환할 위반 자체가 없다(16.2절).
- 저장 실패의 판별에는 오류 메시지 전문을 쓰지 않는다. 드라이버·DB 버전마다 달라지는 문구를 비교하면
  문구가 바뀌는 순간 판별이 조용히 어긋나, 변환해야 할 위반이 500으로 나가거나 숨기면 안 되는 오류가
  성공으로 처리된다. 문구와 독립적인 값으로만 판별하며, 그 값은 저장 경로에 따라 다르다.
  - 영속성 컨텍스트를 거치는 저장(컬렉션 작품)은 Hibernate가 알려 주는 제약조건 **이름**으로 판별한다.
  - JDBC로 실행하는 좋아요 upsert는 Hibernate 예외가 만들어지지 않고 MySQL 드라이버가 제약조건 이름을
    메시지 문자열 안에만 담으므로, MySQL **오류 코드**로 판별한다.
    `collection_like`의 외래 키는 컬렉션을 가리키는 하나뿐이므로(14.3절) "참조 대상 행 없음"
    (`1452`/`1216`)은 사라진 컬렉션 외에 다른 경우가 없다. 이 테이블에 다른 외래 키를 추가하게 되면
    판별을 다시 좁혀야 한다.
- "작품 1개 이상"은 DB 제약조건으로 표현할 수 없으므로 애플리케이션 불변식으로만 보장한다.
- "대표 작품은 포함 작품 중 하나"도 DB 제약조건으로 표현할 수 없으므로 애플리케이션 불변식으로만 보장한다.

## 14. 테이블과 제약조건

이 저장소에는 마이그레이션 도구가 없다. 따라서 테이블 구조는 엔티티의 `@Table`/`@UniqueConstraint`/`@Index` 선언과
이 문서의 표로 관리하고, 실제 개발·운영 DB에는 같은 정의를 별도로 반영한다.
실행 가능한 스크립트는 이 문서에 싣지 않는다. 적용 시점의 스키마와 `user`·`novel` 테이블의 실제 이름은
반영 담당자가 확인해야 하며, 문서에 박아 둔 스크립트는 그 확인 없이 그대로 실행될 수 있기 때문이다.

### 14.1 `collection`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `collection_id` | BIGINT | PK, AUTO_INCREMENT | 컬렉션 PK |
| `user_id` | BIGINT | NOT NULL, FK → `user` | 컬렉션을 만든 사용자 |
| `name` | VARCHAR(20) | NOT NULL | 컬렉션 이름 |
| `description` | VARCHAR(60) | NULL | 컬렉션 설명, 없으면 NULL |
| `is_public` | BOOLEAN | NOT NULL | 공개 여부, DB 기본값을 두지 않고 애플리케이션 생성자가 기본 공개(`true`)를 적용한다 |
| `representative_novel_id` | BIGINT | NOT NULL | 대표 작품, FK를 걸지 않고 애플리케이션이 포함 여부를 보장 |
| `created_date` | DATETIME(6) | NOT NULL | 컬렉션 최초 생성 시점, #561 목록 정렬 기준 |
| `modified_date` | DATETIME(6) | NOT NULL | 최종 수정 시점 |

인덱스: `idx_collection_user_created (user_id, created_date, collection_id)`
— #561의 사용자별 컬렉션 목록을 최초 생성 시점 기준으로 커서 페이지네이션하기 위한 인덱스다.

외래 키 `fk_collection_user (user_id → user)`에는 `ON DELETE CASCADE`를 걸지 않는다(6.1).
`is_public`에는 DB `DEFAULT`를 두지 않는다(3절). 이미 `DEFAULT TRUE`로 만들어진 DB가 있다면
기존 행의 값은 그대로 두고 컬럼 기본값만 제거한다.

### 14.2 `collection_novel`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `collection_novel_id` | BIGINT | PK, AUTO_INCREMENT | 컬렉션 작품 PK |
| `collection_id` | BIGINT | NOT NULL, FK → `collection` | 작품이 포함된 컬렉션 |
| `novel_id` | BIGINT | NOT NULL, FK → `novel` | 컬렉션에 포함된 작품 |
| `created_date` | DATETIME(6) | NOT NULL | 작품이 컬렉션에 추가된 시점, 수정 시 보존한다 |
| `modified_date` | DATETIME(6) | NOT NULL | 최종 수정 시점 |

유니크 제약조건: `uk_collection_novel_collection_novel (collection_id, novel_id)`
인덱스: `idx_collection_novel_collection_created (collection_id, created_date, collection_novel_id)`
— #561의 추가 시점 기준 정렬과 최근 추가 작품 미리보기를 위한 인덱스다. 같은 요청으로 여러 작품을 동시에 추가하면
`created_date`가 같을 수 있으므로 `collection_novel_id`를 함께 정렬 기준으로 사용해 순서를 결정적으로 만든다.

외래 키 `fk_collection_novel_collection (collection_id → collection)`과
`fk_collection_novel_novel (novel_id → novel)`에도 `ON DELETE CASCADE`를 걸지 않는다.
컬렉션 삭제 시 포함 작품 정리는 DB가 아니라 애그리거트의 `cascade`/`orphanRemoval`이 담당한다(6절).

### 14.3 `collection_like`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `collection_like_id` | BIGINT | PK, AUTO_INCREMENT | 컬렉션 좋아요 PK |
| `user_id` | BIGINT | NOT NULL | 좋아요를 누른 사용자, FK를 걸지 않는다 |
| `collection_id` | BIGINT | NOT NULL, FK → `collection` | 좋아요를 받은 컬렉션 |
| `created_date` | DATETIME(6) | NOT NULL | 좋아요를 누른 시점, 좋아요한 컬렉션 목록의 정렬·커서 기준 |
| `modified_date` | DATETIME(6) | NOT NULL | 최종 수정 시점 |

`created_date`와 `modified_date`는 다른 테이블과 달리 `AuditingEntityListener`가 채우지 않는다.
좋아요 등록이 영속성 컨텍스트를 거치지 않는 upsert이므로 DB의 `NOW(6)`로 채운다(12.1절).
애플리케이션 JVM과 DB 서버의 시간대가 다르면 같은 컬럼에 기준이 다른 시각이 섞이므로,
두 시간대가 같은지 확인해야 한다.

유니크 제약조건: `uk_collection_like_user_collection (user_id, collection_id)`
인덱스: `idx_collection_like_user_created (user_id, created_date, collection_like_id)`
— 좋아요한 컬렉션 목록을 좋아요한 시점 기준으로 커서 페이지네이션하기 위한 인덱스다. 같은 시각에 눌린 좋아요가
있을 수 있으므로 `collection_like_id`를 함께 정렬 기준으로 사용해 순서를 결정적으로 만든다.

유니크 제약조건 `(user_id, collection_id)`이 컬렉션별 좋아요 수를 세는 조회의 인덱스 역할을 하지 못하므로,
컬렉션 기준 조회를 받는 인덱스가 따로 필요하다. 유니크 제약조건의 선행 컬럼이 `user_id`이기 때문이다.
좋아요 수는 상세·좋아요 목록 쿼리의 서브 쿼리로만 세므로 `collection_id`로 시작하는 인덱스를 함께 둔다.
`fk_collection_like_collection (collection_id → collection)` 외래 키가 MySQL에서 자동으로 만드는
`collection_id` 인덱스가 이 역할을 하므로 별도 인덱스를 선언하지 않는다.

`user_id`에는 외래 키를 걸지 않는다. 피드 좋아요(`like.user_id`)와 같은 방식이며, 회원 탈퇴가
좋아요를 지우지 않아도 되도록 사용자 행에 묶지 않는다(16.6절).

`fk_collection_like_collection`에는 `ON DELETE CASCADE`를 걸지 않는다. 컬렉션 삭제 시 좋아요 정리는
DB가 아니라 애플리케이션이 담당한다(16.5절). 다른 참조와 같은 이유로, 무엇이 언제 지워지는지가 코드에 드러나야 한다.

이 외래 키는 이름을 엔티티에 명시한다. Hibernate가 붙이는 자동 생성 이름(`FKxxxxxxxx`)은 매핑이 바뀌면
같이 바뀌므로, 실제 DB의 제약조건과 이 매핑이 같은 것을 가리킨다는 사실이 이름에서 읽히지 않는다.
이미 자동 생성 이름으로 만들어진 DB가 있어도 동작은 같지만, 스키마를 손으로 맞추는 이 저장소에서는
이름을 맞춰 두는 편이 낫다.

좋아요 등록 SQL은 이 표의 테이블명·컬럼명과 유니크 제약조건에 그대로 의존한다(12.1절).
컬럼을 이름만 바꿔도 매핑과 달리 애플리케이션이 뜰 때는 드러나지 않고 등록 요청에서만 실패한다.

## 15. 테스트로 검증한 범위와 한계

이 저장소에는 H2나 Testcontainers 같은 DB 통합 테스트 인프라가 없고 `@DataJpaTest`를 사용하는 테스트도 없다.
따라서 단위 테스트로 검증할 수 있는 범위와 실제 DB에서만 확인할 수 있는 범위를 구분한다.

단위 테스트로 검증한 것

- 작품 수 경계값(0/1/2/99/100/101), 중복 작품, 대표 작품 포함 여부, 대표 작품 `null`
- 설명 정규화와 이름 앞뒤 공백 유지
- 생성 시 공개 여부 생략의 기본값 처리와 명시적 `false` 유지, 수정으로 공개 여부를 양방향으로 바꾸는 것
- 수정 DTO가 공개 여부의 `null`을 거부하는 것
- 수정 시 유지되는 작품의 `CollectionNovel` 인스턴스가 교체되지 않고 `createdDate`가 보존되는 것
- 제거된 작품만 빠지고 새 작품만 추가되는 delta 결과
- 소유자·비소유자 판정과 상태 코드
- 검증 순서(컬렉션 존재 → 소유자 → 작품 정책 → 작품 존재)
- 작품 존재 검증이 작품 수와 무관하게 조회 한 번으로 끝나는 것
- 요청 배열 순서 유지
- 응답 상태 코드와 생성 응답의 `collectionId`
- 요청 DTO Bean Validation 메시지
- 유니크 제약조건 위반 판별기의 이름 매칭과 테이블명 접두 정규화
- 포함 작품만 바뀌는 수정과 아무것도 바뀌지 않는 수정이 모두 `modified_date`를 갱신하는 것,
  실패한 수정은 갱신하지 않는 것
- 조회자별 공개 범위(본인은 공개·비공개, 다른 사용자는 공개만, 비로그인은 공개 상세만)
- 어느 방향이든 차단 관계일 때 목록과 상세를 모두 거부하는 것과, 차단 검증이 공개 여부 검증보다 먼저인 것
- 비로그인 상세 조회가 차단 검증을 통과하고 `isMyCollection`이 false인 것
- 커서 왕복(생성 시점과 식별자 보존, 초 미만 정밀도 유지)과 서버가 발급하지 않은 커서 거부
- 요청 크기보다 하나 더 읽어 `hasNext`를 판단하고 초과분을 응답과 미리보기 조회에서 모두 빼는 것
- 마지막 페이지에서 커서를 주지 않는 것과 빈 페이지 응답
- 전체 개수가 페이지 크기와 무관한 것과 `size=3` 재사용
- 허용 범위를 벗어난 페이지 크기를 조회 전에 거부하는 것
- 목록 쿼리가 생성 시점·식별자 내림차순으로 정렬하고 요청한 행 수만 읽는 것,
  본인 조회에만 공개 여부 조건이 빠지는 것, 커서 조건이 생성 시점과 식별자를 함께 비교하는 것
- 미리보기 쿼리가 컬렉션 수와 무관하게 한 번만 실행되고 컬렉션당 상위 N개 조건으로 조립되는 것
- 상세 작품 쿼리가 추가 시점 최신순·오래된순으로 조립되고 식별자를 보조 정렬 기준으로 쓰는 것
- 목록의 대표 작품·최근 추가 작품과 상세의 포함 작품이 모두 같은 네 가지 값의 작품 요약으로 나가는 것
- 대표 작품이 최근 추가 작품에 포함돼도 서버가 중복을 제거하지 않고 그대로 함께 내보내는 것
- 최근 추가 작품을 컬렉션당 최대 5개까지만 조회하는 것
- 상세가 소유자 정보를 `owner` 객체로 묶어 내보내고 `owner.avatarImage`가 비어 있지 않은 것
- 상세 조회가 소유자 아바타를 inner join으로 읽고 작품 통계를 조인하지 않는 것
- 수정·삭제 대상 조회가 잠금 쿼리를, 조회 전용 경로가 잠금 없는 쿼리를 사용하는 것
- 잠금 쿼리가 `setLockMode(PESSIMISTIC_WRITE)`로 조립되고 작품을 조인하지 않는 것,
  조회 전용 쿼리는 잠금을 걸지 않고 `fetchJoin()`으로 자식을 함께 읽는 것
  (`JPAQueryFactory`를 대역으로 두고 조립된 쿼리를 확인한다)
- 탈퇴 정리 쿼리가 `collection.user_id`만 `-1`로 바꾸는 `update`로 조립되고 대상 조건이 탈퇴 사용자인 것,
  컬렉션을 조회하거나 삭제하지 않는 것
- 회원 탈퇴 시 소유자 이관이 사용자 삭제보다 먼저, 피드·댓글 작성자 익명화와 나란히 일어나는 것과,
  이관 실패 시 사용자를 지우지 않는 것
- 공개 컬렉션과 본인 비공개 컬렉션에는 좋아요를 누를 수 있고 다른 사용자의 비공개 컬렉션에는 누를 수 없는 것,
  자신의 컬렉션에도 좋아요를 누를 수 있는 것
- 좋아요 등록·취소가 존재하지 않는 컬렉션과 차단 관계 컬렉션을 거부하는 것과,
  차단 검증이 공개 여부 검증보다 먼저인 것
- 좋아요하지 않은 컬렉션의 취소가 오류가 아닌 것
- 좋아요 등록 SQL이 `collection_like`의 컬럼명과 사용자·컬렉션 순서로 조립되고,
  `ON DUPLICATE KEY UPDATE`로 기존 행의 시각을 바꾸지 않는 no-op을 실행하며, `INSERT IGNORE`가 아닌 것
  (`JdbcTemplate`을 대역으로 두고 실행된 문장과 바인딩 값을 확인한다)
- 등록이 사전 존재 확인 없이 upsert 한 문장으로 끝나는 것과, 같은 요청을 반복해도 실패 판별기를
  건드리지 않는 것
- 등록이 갱신 행 수를 결과로 내보내지 않는 것(리포지토리와 Service 모두 반환형이 `void`인 것)
- 좋아요 등록 유스케이스가 바깥 트랜잭션을 열지 않는 것과, 등록하는 Service가 `@Transactional`
  하나로 경계를 관리하는 것(클래스·메서드의 `@Transactional` 선언을 확인한다)
- 등록하는 Service가 트랜잭션 경계를 코드로 다루는 필드를 두지 않고, 다른 Service에도 의존하지 않는 것
- 등록하는 사이에 컬렉션이 삭제된 무결성 오류는 404 `COLLECTION-001`로 바꾸고, 판별하지 못한 무결성
  오류는 그대로 던지는 것, 어느 경우든 삼키고 정상 반환하지 않는 것
- 유스케이스가 제약조건 판별기에 의존하지 않고, 등록 계층이 처리하지 않은 무결성 예외를
  대신 해석하지 않으며, 등록 계층이 올린 컬렉션 도메인 예외는 그대로 통과시키는 것
- 좋아요 취소 유스케이스는 접근 검증과 삭제를 하나의 트랜잭션으로 묶는 것
- 좋아요 등록이 컬렉션 존재 확인, 차단 검증, 등록 순서로 각자의 트랜잭션을 쓰는 것
- 접근 검증이 컬렉션 엔티티가 아니라 값(`CollectionAccess`)을 돌려주고, 등록에도 식별자만 넘기는 것
- 좋아요 커서 왕복(좋아요 시점과 좋아요 식별자 보존, 초 미만 정밀도 유지)과 서버가 발급하지 않은 커서 거부
- 좋아요 목록 쿼리가 좋아요 시점·좋아요 식별자 내림차순으로 정렬하고 요청한 행 수만 읽는 것,
  커서 조건이 두 값을 함께 비교하는 것
- 좋아요 목록 쿼리가 공개 컬렉션과 조회자 본인 컬렉션만 남기고, 차단 관계 사용자의 컬렉션을 빼는 것,
  차단 관계가 없으면 제외 조건을 넣지 않는 것
- 좋아요 목록의 전체 개수를 목록과 같은 공개 범위·차단 조건으로 세는 것
- 좋아요 목록 카드가 좋아요 수와 최근 추가 작품 미리보기를 담는 것
- 좋아요 취소와 컬렉션 좋아요 정리가 대상 행을 엔티티로 읽지 않고 벌크 삭제로 조립되는 것
- 컬렉션 삭제가 좋아요를 컬렉션보다 먼저 지우는 것과, 소유자가 아니면 좋아요도 지우지 않는 것
- 상세 응답이 좋아요 수와 조회자의 좋아요 여부를 함께 내보내는 것,
  좋아요 수를 따로 조회하지 않는 것, 비로그인 조회의 `isLiked`가 false인 것
- 좋아요 실패 판별기가 "참조 대상 행 없음" 오류 코드만 사라진 컬렉션으로 보고 유니크 위반·NOT NULL
  위반은 그렇게 보지 않는 것, 원인 체인 깊은 곳의 SQL 예외도 찾는 것, 메시지 문구에 기대지 않는 것

자동 테스트로 강제하지 않는 것

엔티티 매핑 메타데이터(테이블명, 유니크 제약조건, 인덱스, cascade와 orphanRemoval, 컬럼 길이와 nullable,
공개 여부의 원시 타입과 `columnDefinition` 부재)와 리포지토리·트랜잭션 구조 규약(`@Query` 미사용,
트랜잭션 속성 명시와 경계 위치)은 3·12·13·14절과 `CLAUDE.md` 코드 컨벤션이 정의하고 코드 리뷰로 지킨다.

실제 DB에서만 확인할 수 있는 것

- 14절의 유니크 제약조건 `uk_collection_novel_collection_novel`과 `uk_collection_like_user_collection`이
  실제 DB에서 중복 저장을 막는지
- 컬렉션 삭제 시 `collection_novel`이 실제로 함께 삭제되는지와, 좋아요를 먼저 지워 외래 키 위반 없이 끝나는지
- 동시에 같은 작품을 추가하는 요청에서 제약조건 위반이 `COLLECTION-003`으로 변환되는지
- 좋아요 등록 SQL이 실제 스키마에서 실행되는지. 단위 테스트는 조립된 문장까지만 확인할 수 있고,
  테이블명·컬럼명·유니크 제약조건이 실제 DB와 맞는지는 DB 없이는 증명할 수 없다
- 중복 등록이 실제로 멱등하게 끝나는지. 같은 사용자의 동시 `PUT` 두 건이 모두 204로 끝나고
  `collection_like` 행이 하나만 남는지, 두 번째 요청이 기존 행의 `created_date`를 바꾸지 않아
  좋아요한 컬렉션 목록의 순서가 유지되는지
- `NOW(6)`로 채운 시각이 애플리케이션이 채운 다른 테이블의 감사 필드와 같은 시간대인지
- 좋아요 등록 요청 하나가 커넥션을 한 번에 하나만 점유하는지. 단위 테스트는 바깥 트랜잭션이 없다는
  구조까지만 확인할 수 있고, 커넥션 풀 크기를 1로 줄인 상태에서 등록이 끝까지 진행되는지는
  실제 DataSource 없이는 증명할 수 없다
- 좋아요 등록과 컬렉션 삭제의 경쟁이 실제로 외래 키 잠금 순서대로 갈리는지. 등록이 먼저면 삭제가
  대기했다가 그 좋아요까지 지우고 끝나는지, 삭제가 먼저면 등록이 500이 아니라
  404 `COLLECTION-001`로 끝나는지
- MySQL이 참조 대상 없는 INSERT에 실제로 오류 코드 `1452`를 돌려주는지와, 그 예외가 Spring의
  `DataIntegrityViolationException`으로 변환되어 판별기까지 도달하는지
- 외래 키 `fk_collection_like_collection`이 실제 DB에 이 이름으로 존재하는지
- 인덱스가 목록·상세 조회 쿼리에 실제로 사용되는지
- 쓰기 잠금이 실제로 동시 수정을 직렬화하는지와 잠금 대기·교착 상태가 없는지.
  단위 테스트는 쿼리에 `PESSIMISTIC_WRITE`가 지정된다는 사실까지만 확인할 수 있고,
  MySQL이 실제로 `SELECT ... FOR UPDATE`를 실행해 동시 요청을 막는지는 DB 없이는 증명할 수 없다
- `fetchJoin()`으로 자식을 함께 읽어 실제로 추가 조회(N+1)가 발생하지 않는지
- 목록·상세 조회가 실제 DB에서 의도한 개수의 쿼리만 실행하는지와, 컬렉션별 상위 N개 조건의 실행 계획
- 페이지 사이에 컬렉션이 추가·삭제될 때 커서가 실제로 중복·누락을 막는지
- 회원 탈퇴가 FK 위반 없이 끝나는지와, 이관된 컬렉션이 실제로 `user_id = -1`로 남아 보존되는지
- 명시적으로 표시한 `modified_date`가 auditing에 덮어써지지 않고 그대로 저장되는지

## 16. 컬렉션 좋아요

- 좋아요는 사용자가 컬렉션에 표시하는 관심이며 컬렉션과 별도의 애그리거트다.
- 같은 사용자와 컬렉션 조합의 좋아요는 하나만 저장한다.
- 로그인한 사용자만 좋아요를 등록하거나 취소할 수 있다.
- 자신이 만든 컬렉션에도 좋아요를 누를 수 있다.
- 좋아요를 누른 시점(`collection_like.created_date`)은 좋아요한 컬렉션 목록의 정렬 기준이다.
- 좋아요를 취소했다가 다시 누르면 새 행이 되므로 목록에서도 다시 누른 시점으로 올라온다.

좋아요 수는 컬렉션이 받은 전체 좋아요 수이며 조회자와 무관하다. 공개 컬렉션이 비공개로 바뀌어도
좋아요 데이터와 좋아요 수는 그대로 유지한다. 비공개 전환은 누가 볼 수 있는지를 바꿀 뿐,
이미 눌린 좋아요를 없던 일로 만들지 않는다.

### 16.1 등록과 취소는 볼 수 있는 컬렉션에만 할 수 있다

`PUT /collections/{collectionId}/likes`와 `DELETE /collections/{collectionId}/likes`를 사용하며
성공하면 둘 다 `204 No Content`를 반환한다.

1. 컬렉션이 존재하는지 확인한다.
2. 요청한 사용자와 소유자가 차단 관계인지 확인한다.
3. 비공개 컬렉션이면 소유자인지 확인한다.
4. 좋아요한 상태로 만들거나 좋아요를 지운다.

- 접근 정책과 검증 순서는 상세 조회(10절)와 같다. 볼 수 없는 컬렉션에 좋아요를 누를 수 없어야 하고,
  판정이 화면마다 갈리면 상세에서 보이지 않는 컬렉션에 좋아요가 쌓일 수 있다.
- 취소도 등록과 같은 정책을 적용한다. 볼 수 없게 된 컬렉션은 목록에서도 숨기므로(16.4절)
  취소할 방법이 사라지지 않는다.
- 비공개 판정은 컬렉션 도메인이 소유한다. 좋아요는 컬렉션에서 뽑아 낸 값인 `CollectionAccess`의
  `validateVisibleTo`로 판정하므로, 접근 검증 트랜잭션이 닫힌 뒤에도 같은 규칙을 그대로 쓴다(12.6절).
- 등록에 `POST`가 아니라 `PUT`을 쓰는 이유는 16.2절과 같다. 요청이 "좋아요를 하나 더 만든다"가 아니라
  "좋아요한 상태로 만든다"를 뜻한다.

### 16.2 등록과 취소는 멱등하다

같은 요청을 반복해도 최종 상태가 같고 응답도 같다.

- 이미 좋아요한 컬렉션에 다시 등록해도 좋아요는 하나만 남고 `204`를 반환한다.
- 좋아요하지 않은 컬렉션의 취소 요청도 오류가 아니라 `204`를 반환한다.
- 따라서 클라이언트는 현재 좋아요 상태를 몰라도 원하는 최종 상태만 보내면 된다.
  화면과 서버의 상태가 어긋났을 때 사용자에게 오류를 보여 줄 이유가 없다.

등록의 멱등성은 애플리케이션이 아니라 DB가 보장한다. 존재 여부를 먼저 확인해도 동시 요청은 둘 다 통과한 뒤
유니크 제약조건에서 갈리므로, 확인하는 대신 중복을 흡수하는 한 문장을 실행한다.

```
INSERT INTO collection_like (user_id, collection_id, created_date, modified_date)
VALUES (?, ?, NOW(6), NOW(6))
ON DUPLICATE KEY UPDATE collection_like_id = collection_like_id
```

- 중복이면 `ON DUPLICATE KEY UPDATE`가 PK를 자기 자신으로 대입하는 no-op을 실행하고 정상 종료한다.
  잡을 예외가 없으므로 사전 존재 확인도, 위반을 멱등한 성공으로 바꾸는 처리도 필요 없다.
- 기존 행의 `created_date`와 `modified_date`를 바꾸지 않는다. `created_date`가 좋아요한 컬렉션 목록의
  정렬·커서 기준이므로(16.4절), 같은 요청을 반복했다고 목록 순서가 흔들리면 안 된다.
- `INSERT IGNORE`를 쓰지 않는다. 유니크 위반뿐 아니라 외래 키 위반까지 삼켜, 사라진 컬렉션에 대한
  좋아요가 조용히 성공으로 끝난다(16.7절).
- 이 호출이 실제로 행을 넣었는지는 알리지 않는다. MySQL의 갱신 행 수는 커넥터 설정
  (`CLIENT_FOUND_ROWS`)에 따라 중복에서 0이 되기도 1이 되기도 하므로 근거로 삼을 수 없고,
  API는 어차피 최종 상태(`204`)만 보장한다.
- 남는 실패인 "사라진 컬렉션"의 판별은 등록하는 계층(`CollectionLikeService`)이 끝내고 유스케이스에는
  넘기지 않는다. 유스케이스는 접근 정책만 판단한다(12.5절, 16.7절).

### 16.3 좋아요 수는 컬렉션 조회가 함께 읽는다

컬렉션 상세(`GET /collections/{collectionId}`)는 `likeCount`와 `isLiked`를 함께 내보낸다.

- `likeCount`는 컬렉션이 받은 전체 좋아요 수이고 조회자와 무관하다. 컬렉션 자체의 값이므로 상세 쿼리의
  서브 쿼리로 함께 읽는다. 따로 조회하면 상세를 그리는 쿼리 수가 좋아요 때문에 늘어난다.
- `isLiked`는 조회자가 좋아요를 눌렀는지이며 조회자별 값이므로 컬렉션을 읽는 쿼리에 담지 않고 따로 확인한다.
  비로그인 조회는 좋아요를 누를 수 없으므로 조회 없이 항상 `false`다.
- 따라서 상세를 그리는 쿼리는 비로그인 2개(컬렉션·포함 작품), 로그인 3개(좋아요 여부 추가)다.
- 사용자별 컬렉션 목록(8절)의 카드에는 좋아요 수를 넣지 않는다. #562의 제외 범위가 일반 목록 조회이므로
  기존 응답을 바꾸지 않는다. 필요해지면 별도 이슈로 다룬다.

### 16.4 좋아요한 컬렉션 목록은 좋아요한 순서로 본다

`GET /users/me/liked-collections`를 사용하며 로그인한 사용자만 요청할 수 있다.
성공하면 `200 OK`를 반환한다.

1. 페이지 크기가 1 이상 100 이하인지 확인한다.
2. 조회자와 차단 관계인 사용자를 한 번에 읽는다.
3. 커서 다음 좋아요를 요청 크기보다 하나 더 읽어 다음 페이지 존재 여부를 판단한다.
4. 이번 페이지 컬렉션의 최근 추가 작품 미리보기를 한 번의 조회로 채운다.

- 본인 목록만 조회하므로 경로에 사용자 ID를 받지 않는다.
- 목록은 컬렉션을 만든 시점이 아니라 좋아요를 누른 시점 내림차순으로 정렬한다.
  컬렉션 생성 시점 기준으로 정렬하면 목록 순서가 좋아요라는 행위와 무관해진다.
- 커서는 마지막으로 읽은 **좋아요**의 `created_date`와 `collection_like_id`를 담는다.
  사용자별 컬렉션 목록의 커서(8.1절)와 담는 값이 다르므로 두 목록 사이에서 바꿔 쓸 수 없다.
- 나머지 커서 규칙(불투명한 Base64 문자열, 서버가 발급하지 않은 커서 거부, `hasNext`와 커서 유무 일치)은
  8.1절과 같다.
- 카드는 사용자별 컬렉션 목록의 카드와 같은 값에 `likeCount`를 더한다. 목록에 담긴 컬렉션은 모두 조회자가
  좋아요한 컬렉션이므로 좋아요 여부는 따로 내보내지 않는다.
- 인덱스 `idx_collection_like_user_created (user_id, created_date, collection_like_id)`가
  이 정렬과 커서 조건을 받는다.

공개 범위는 저장 시점이 아니라 조회 시점에 판단한다. 좋아요를 누른 뒤 컬렉션이 비공개로 바뀌거나
소유자와 차단 관계가 되어도 좋아요 자체는 남아 있기 때문이다.

| 좋아요한 컬렉션 | 목록 노출 |
|---|---|
| 공개 컬렉션 | 노출 |
| 본인이 만든 비공개 컬렉션 | 노출 |
| 다른 사용자의 비공개 컬렉션 | 숨김 |
| 차단 관계 사용자의 컬렉션 | 숨김 |

- 차단은 어느 방향이든 적용한다(10절).
- 사용자별 컬렉션 목록과 달리 목록 자체를 거부하지 않고 해당 컬렉션만 걸러 낸다.
  여러 사용자의 컬렉션이 섞이는 목록이므로, 한 사용자와의 차단 때문에 목록 전체를 막을 수 없다.
- 숨긴 컬렉션은 `collectionsCount`에도 세지 않는다. 보이는 개수와 표시하는 개수가 어긋나면
  사용자가 목록에서 찾을 수 없는 컬렉션을 계속 세게 된다.

### 16.5 컬렉션을 지우면 좋아요를 먼저 지운다

- 좋아요는 별도 애그리거트라 컬렉션 엔티티에 매핑하지 않으므로 `cascade`로 따라 지워지지 않는다.
- `collection_like.collection_id`가 컬렉션을 참조하므로 좋아요가 남아 있으면 컬렉션 삭제가 실패한다.
- 따라서 `CollectionManagementApplication.delete`가 좋아요를 먼저 지우고 컬렉션을 지운다.
- 소유자 검증에 실패한 삭제는 좋아요도 건드리지 않는다.
- 좋아요 정리는 지울 행을 엔티티로 읽지 않고 한 번의 벌크 삭제로 끝낸다.
- 삭제는 대상 컬렉션을 쓰기 잠금으로 먼저 잡는다. 그 사이에 들어온 좋아요 등록과의 경쟁은
  DB의 외래 키 잠금이 가른다(16.7절).

### 16.6 탈퇴한 사용자가 남긴 좋아요는 지우지 않는다

- `collection_like.user_id`에 외래 키를 걸지 않으므로 사용자를 지워도 좋아요는 남는다.
  피드 좋아요(`like.user_id`)와 같은 방식이며, 탈퇴 흐름에 좋아요 정리를 추가하지 않는다.
- 컬렉션은 탈퇴해도 보존되므로(6.1절) 컬렉션에 달린 좋아요도 정리할 필요가 없다.
- 남은 좋아요는 좋아요 수에 계속 포함된다. 탈퇴한 사용자의 좋아요를 좋아요 수에서 뺄지는 피드 좋아요와
  함께 정할 문제이며, 컬렉션만 다르게 처리하지 않는다.

### 16.7 컬렉션 삭제와 좋아요 등록의 경쟁은 DB가 가르고 결과만 404로 옮긴다

좋아요는 컬렉션을 참조하므로, 좋아요를 등록하는 사이에 컬렉션이 삭제되면 참조 대상 행이 없어진다.
아무 처리도 하지 않으면 이 경쟁이 외래 키 위반, 곧 클라이언트에게는 `500`으로 나간다.

이 경쟁은 애플리케이션이 잠금으로 직렬화하지 않고 DB의 외래 키 잠금 순서에 맡긴다.
InnoDB는 자식 행을 넣을 때 부모 행을 잡고 부모를 지울 때도 같은 행을 잡으므로, 두 요청은 어차피
그 행에서 갈린다. 애플리케이션이 부모를 다시 조회해 공유 잠금을 걸어도 같은 직렬화를 한 번 더 얻을 뿐이고,
등록 경로에는 조회 왕복과 잠금이 하나 늘어난다.

| 순서 | 결과 |
|---|---|
| 등록이 먼저 | 삭제가 등록 커밋까지 대기했다가 그 좋아요까지 함께 지우고 끝난다 |
| 삭제가 먼저 | 등록이 `fk_collection_like_collection` 위반으로 끝난다 → `COLLECTION-001`(404) |

- 외래 키 위반은 서버 오류가 아니라 컬렉션을 찾을 수 없는 요청이므로 `CollectionLikeService`가
  `COLLECTION-001`로 바꿔 던진다. 예외를 던지므로 등록 트랜잭션은 롤백된다.
- 위반의 판별 근거는 13절에 있다. 판별하지 못한 무결성 오류는 숨기지 않고 그대로 재전파한다.
- 유니크 위반은 여기서 다루지 않는다. upsert가 흡수하므로 예외로 올라오지 않는다(16.2절).
- 취소에는 이 처리가 필요 없다. 지우는 쪽은 참조 대상이 이미 사라졌어도 지울 행이 없을 뿐이다.

## 17. 아직 확정되지 않은 정책

- 작품이 삭제될 때 해당 작품을 포함한 컬렉션을 어떻게 처리할지는 정하지 않았다.
  현재는 `collection_novel.novel_id`에 FK가 있어 작품을 지우려면 컬렉션 작품을 먼저 정리해야 한다.
  이 경우 컬렉션이 작품 0개가 되거나 대표 작품을 잃을 수 있다. #559가 "삭제된 작품의 컬렉션 보존 정책"을
  제외 범위로 두었으므로 별도로 결정한다.
- 컬렉션 이름과 설명의 개행·이모지 처리는 기존 피드와 동일하게 별도 처리를 하지 않는다.

사용자 탈퇴 시 컬렉션 처리는 6.1절에서 확정했다. DB `ON DELETE CASCADE`가 아니라 애플리케이션이
소유자를 알 수 없는 사용자로 넘기고 컬렉션은 보존한다.
