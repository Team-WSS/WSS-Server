# 차단 정책

이 문서는 사용자 차단 기능에서 지켜야 하는 도메인 규칙과 각 기능의 처리 흐름을 정리한다.
현재 적용 범위는 사용자 프로필·서재, 피드·댓글·신고, 알림, 인기 작품 조회이며 컬렉션은 포함하지 않는다.

## 1. 차단 관계

- 차단 데이터는 `차단한 사용자(blocking)`에서 `차단된 사용자(blocked)`로 향하는 단방향 관계이다.
- 콘텐츠 접근과 노출 여부를 판단할 때는 양방향 관계로 해석한다.
  - A가 B를 차단했거나 B가 A를 차단했다면 두 사용자는 차단 관계이다.
- A가 B를 차단하면 B는 A의 프로필과 콘텐츠에 접근할 수 없으므로, 정상적인 서비스 흐름에서는 B가 A를 다시 차단할 수 없다.
- 따라서 한 사용자 쌍에는 먼저 생성된 한 방향의 차단 관계만 존재하는 것을 정상 상태로 본다.
- 자기 자신과는 차단 관계로 판단하지 않는다.
- 비로그인 사용자는 특정 사용자와 차단 관계가 없는 것으로 처리한다.
- 차단 목록에는 자신이 차단한 사용자만 노출한다. 자신을 차단한 사용자는 노출하지 않는다.

## 2. 차단 생성

### 2.1 공통 검증

차단 생성 요청은 다음 순서로 검증한다.

1. 로그인한 사용자의 요청인지 확인한다.
2. 자기 자신을 차단하려는 요청인지 확인한다.
3. 차단 대상 사용자가 존재하는지 확인한다.
4. 차단 대상이 관리자인지 확인한다.
5. 현재 사용자를 `blocking`, 대상 사용자를 `blocked`로 차단 관계를 저장한다.

자기 자신과 관리자는 차단할 수 없다.

### 2.2 기존 차단 API

- `POST /blocks?userId={blockedUserId}`를 사용한다.
- 신규 차단과 중복 차단 요청 모두 기존 응답 정책에 따라 `201 Created`를 반환한다.
- 기존 클라이언트 호환을 위해 동작은 유지하지만 Deprecated 대상이다.

### 2.3 멱등 차단 API

- `PUT /blocks/users/{blockedUserId}/v2`를 사용한다.
- 차단 관계를 처음 생성한 요청과 이미 존재하는 차단을 다시 요청한 경우 모두 `204 No Content`를 반환한다.
- 중복 여부는 `(blocking_id, blocked_id)` 유니크 제약조건을 최종 기준으로 판단한다.
- 동시에 같은 차단 요청이 들어오더라도 한 건만 저장하고, 중복 요청은 성공으로 처리한다.
- 지정한 차단 유니크 제약조건 위반만 멱등 성공으로 처리한다. 그 외 데이터 무결성 오류는 숨기지 않는다.

## 3. 차단 해제

- `DELETE /blocks/{blockId}`를 사용한다.
- 차단 데이터가 없으면 `404 Not Found`를 반환한다.
- 차단을 생성한 사용자만 해당 차단을 해제할 수 있다.
- 다른 사용자가 생성한 차단을 해제하려는 경우 `403 Forbidden`을 반환한다.
- 차단을 해제하면 두 사용자 사이의 차단 관계와 콘텐츠 접근 제한이 함께 해제된다.
- 현재 차단 해제 API는 존재하지 않는 차단을 성공으로 처리하지 않으므로 멱등 API가 아니다.

## 4. 차단 목록 조회

- 로그인한 사용자가 직접 차단한 사용자만 조회한다.
- 최신 차단이 먼저 보이도록 `blockId` 내림차순으로 정렬한다.
- 응답에는 차단 ID, 차단된 사용자 ID, 닉네임, 아바타 정보를 포함한다.
- 차단 관계와 사용자·아바타 정보를 한 번의 조회로 가져온다.

## 5. 차단 관계 검증

두 사용자 사이의 접근 가능 여부는 다음과 같이 판단한다.

1. 두 사용자 ID가 같으면 접근을 허용한다.
2. 요청 사용자가 비로그인 상태이면 차단 검증을 생략한다.
3. `요청 사용자 → 대상 사용자` 또는 `대상 사용자 → 요청 사용자` 차단이 존재하는지 조회한다.
4. 어느 한 방향이라도 존재하면 차단된 접근으로 처리하고 `403 Forbidden`을 반환한다.

차단 검증은 Controller가 아니라 해당 기능의 Application 또는 Service 계층에서 수행한다. 따라서 HTTP 진입점이 달라져도 같은 정책을 적용한다.

## 6. 사용자 프로필과 서재

프로필·서재 조회는 다음 순서로 처리한다.

1. 조회 대상 사용자가 존재하는지 확인한다.
2. 로그인 사용자와 조회 대상 사용자 사이의 차단 관계를 확인한다.
3. 차단 관계가 없다면 프로필 공개 범위와 요청 기능별 접근 조건을 확인한다.
4. 모든 검증을 통과한 경우에만 프로필·서재 데이터를 조회한다.

프로필 상세, 선호 키워드, 작품 통계, 장르 취향, 작품 상태별 목록 등 프로필 하위 조회 API도 동일한 차단 검증을 적용한다.

## 7. 피드와 댓글

### 7.1 목록 조회

- 피드 목록에서는 로그인 사용자와 차단 관계인 사용자가 작성한 피드를 제외한다.
- 댓글 목록과 댓글 수에서는 로그인 사용자와 차단 관계인 사용자가 작성한 댓글을 제외한다.
- 작품 피드, 인기 피드, 추천 피드, 소셜 피드 등 피드 작성자가 노출되는 목록에는 같은 기준을 적용한다.
- 비로그인 조회에서는 차단 관계를 적용하지 않는다.

### 7.2 상세 조회와 변경 요청

피드 상세 조회, 좋아요, 댓글 작성, 신고 등 특정 피드나 댓글을 대상으로 하는 요청은 대상 조회 후 다음 기준을 적용한다.

- 피드 상세 조회·좋아요·댓글 작성처럼 피드를 기준으로 처리하는 요청은 요청 사용자와 피드 작성자의 관계를 검증한다.
- 댓글 목록을 조회할 때는 피드 작성자와의 차단 관계를 먼저 검증하고, 차단 관계인 댓글 작성자의 댓글은 결과에서 제외한다.
- 댓글 신고처럼 피드와 댓글에 모두 접근하는 요청은 피드 작성자와 댓글 작성자를 모두 검증한다.
- 피드 작성자와 댓글 작성자가 같다면 같은 차단 검증을 중복 수행하지 않는다.

차단 관계라면 대상 ID를 직접 알고 있더라도 조회·좋아요·댓글·신고를 허용하지 않는다.

## 8. 인기 작품 조회

- 인기 작품을 계산할 때 차단 관계인 사용자의 피드는 후보에서 제외한다.
- 작품 설명에 대표 피드 내용을 사용하는 경우에도 노출 가능한 피드만 사용한다.
- 노출 가능한 피드가 없으면 작품의 기본 설명을 사용한다.

## 9. 알림

차단 관계인 사용자 사이에는 피드 댓글 알림을 생성하지 않는다.

댓글 작성 후 알림 대상은 다음과 같이 정한다.

1. 피드 작성자와 새 댓글 작성자가 서로 다른지 확인한다.
2. 두 사용자가 차단 관계가 아니면 피드 작성자에게 알림을 생성한다.
3. 기존 댓글 작성자 중 새 댓글 작성자 본인, 피드 작성자, 중복 사용자를 제외한다.
4. 남은 사용자 중 새 댓글 작성자와 차단 관계인 사용자를 제외한다.
5. 최종 대상에게만 알림을 생성하고 푸시 전송을 요청한다.

차단 생성 또는 해제 자체에 대한 알림은 생성하지 않는다.

## 10. 데이터 무결성

- 동일한 사용자가 같은 사용자를 여러 번 차단한 데이터가 저장되지 않아야 한다.
- `(blocking_id, blocked_id)` 유니크 제약조건을 애플리케이션 엔티티와 실제 개발·운영 DB에 동일하게 적용한다.
- 차단 유니크 제약조건 이름은 `uk_block_blocking_blocked`를 사용한다.
- 멱등 차단 API는 저장 시점에 제약조건 위반을 확인할 수 있도록 즉시 반영한 뒤, 해당 제약조건의 중복만 차단 도메인 예외로 변환한다.

## 11. 아직 확정되지 않은 정책

- 차단 해제 API를 멱등 방식으로 추가할지는 별도로 결정한다.
- 사용자 탈퇴 시 해당 사용자의 발신·수신 차단 이력을 어떻게 정리할지는 탈퇴 정책과 함께 결정한다.
- 컬렉션 기능에는 현재 차단 정책이 적용되어 있지 않으며, 컬렉션 개발 시 공개 범위 및 비로그인 공유 링크 정책과 함께 반영한다.
